2. NON-NEGOTIABLE PROJECT RULES

Follow these rules throughout the entire project.

2.1 Preserve the existing project

1.  Never replace the existing project with a newly generated template.
2.  Never discard existing working functionality just to simplify
    implementation.
3.  Never arbitrarily change the programming language, framework,
    backend, database or hosting provider.
4.  Never remove existing API endpoints without proving they are
    obsolete and documenting their replacement.
5.  Never change existing API contracts without updating all affected
    clients.
6.  Never overwrite working authentication, messaging, database or
    deployment functionality without understanding its dependencies.
7.  Preserve existing application identity, package identifiers,
    repository structure and essential configuration.
8.  Keep backward compatibility wherever practical.
9.  Use migrations for database changes. Never casually delete or
    recreate production databases.
10. Never introduce fake functionality, simulated responses or
    placeholder success messages into production features.

2.2 Evidence before implementation

Before changing anything:

-   Inspect the relevant source code.
-   Identify the actual implementation.
-   Trace the complete execution path.
-   Identify affected components and dependencies.
-   Check existing tests.
-   Determine whether another implementation already exists.
-   Document the proposed change.
-   Identify risks and rollback procedures.

Do not implement a feature twice because you failed to discover an
existing implementation.

2.3 No destructive shortcuts

Never:

-   Delete databases to resolve migration errors.
-   Replace configuration files without examining their contents.
-   Remove authentication checks to make a feature work.
-   Disable security controls to bypass an error.
-   Remove existing screens or routes without a documented reason.
-   Expose API keys, passwords, signing credentials, JWT secrets, TURN
    credentials or private configuration.
-   Commit secrets into Git.
-   Perform a production deployment without explicit authorization.
-   Force-push, rewrite Git history or delete branches without explicit
    authorization.

2.4 No fabricated completion

Never mark a feature as completed because:

-   A screen exists.
-   A button is visible.
-   An API endpoint returns HTTP 200.
-   A database table exists.
-   A mock response works.
-   A local demonstration succeeds.
-   The code compiles without testing its actual behavior.

Completion requires evidence.

executed concurrently.

Evaluate failure consistency and durable event recovery.

Finding 4: Group member information

Previously observed: the group member listing endpoint did not appear to
enforce membership before returning user information.

Verify current authorization.

Finding 5: Status privacy

Previously observed: stored status privacy settings did not appear to be
fully enforced during feed retrieval and direct viewing.

Verify feed and direct-access authorization.

Finding 6: Status views

Previously observed: status viewing and viewer-list routes appeared to
lack complete ownership/viewer authorization.

Verify both operations.

Finding 7: Message reactions

Previously observed: reaction updates appeared to lack complete
conversation-participant authorization.

Verify the current route.

Finding 8: Password hashing

Previously observed: PBKDF2-HMAC-SHA256 used 100,000 iterations.

Compare the current configuration against current OWASP guidance.
Evaluate appropriate password hashing parameters and migration of
existing password hashes.

Finding 9: Group calls

Previously observed: group calling used mesh topology.

Evaluate scalability and whether an SFU is required.

Finding 10: Migrations and runtime dependencies

Previously observed: migration scripts may not cover every migration,
and Wrangler/runtime dependencies may need review.

Verify all migration files and actual deployment procedures.

Required end-to-end scenarios

Scenario 8: Multi-device

Login on two devices → Send messages from each → Verify synchronization
→ Read on one device → Verify appropriate status updates on the other.

15. MULTI-AGENT COORDINATION RULES

Multiple agents may work on the project.

They must behave like one engineering team.

15.1 Shared source of truth

Every agent must read agent.md before starting.

No agent may create its own conflicting feature-status document.

All agents must update the same central project memory.

15.2 Task ownership

Before working, an agent must record:

-   Assigned task.
-   Relevant files.
-   Expected changes.
-   Dependencies.
-   API contracts involved.
-   Database changes.
-   Testing requirements.
-   Potential conflicts.

15.3 Avoid simultaneous conflicting edits

Do not let two agents independently modify the same critical files
without coordination.

Examples:

-   Authentication middleware.
-   Database migrations.
-   API types.
-   Message models.
-   WebSocket handlers.
-   Application navigation.
-   Global state management.

If work overlaps, coordinate the changes and define one owner for
integration.

15.4 Agent handover

Every completed task must include:

Task:
Agent:
Start commit:
End commit:
Files modified:
Database changes:
API changes:
Tests executed:
Test results:
Known limitations:
Remaining work:
Next recommended task:

Never leave the next agent guessing what happened.

15.5 Prevent duplicate work

Before implementing anything:

1.  Search agent.md.
2.  Search the source tree.
3.  Check recent commits.
4.  Check the feature matrix.
5.  Verify actual implementation.

If the feature already exists, test and improve it rather than
recreating it.

1.  Define the problem.
2.  Document the current behavior.
3.  Define expected behavior.
4.  Identify affected components.
5.  Create a minimal implementation plan.
6.  Implement the change.
7.  Run relevant tests.
8.  Run regression tests.

18. DEFINITION OF DONE

A feature is complete only when:

-   Its expected behavior is documented.
-   Its implementation exists.
-   It is integrated into the actual application.
-   Its API and database behavior are correct.
-   Authentication is enforced.
-   Authorization is enforced.
-   Input validation exists.
-   Error handling exists.
-   Loading and empty states exist where relevant.
-   Offline behavior is addressed where relevant.
-   Tests pass.
-   Existing functionality has not regressed.
-   Documentation is updated.
-   The next agent can understand the implementation.

A visible button without a working backend is not a completed feature.

A successful API response without authorization tests is not a completed
feature.

A successful local demo without synchronization and recovery testing is
not a completed feature.
